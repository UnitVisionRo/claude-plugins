**Never create migration files manually**, always use alembic to create the migration.

-  Create a migration.
    ```bash
    alembic revision [--autogenerate] -m "your message"
    ```

- Do not add collation/charset directives; let the DB server decide.

- **Always read the generated migration before running it.** `--autogenerate` diffs the models
  against the live schema, and there are changes it does not detect at all — see the per-engine
  notes below, and **CHECK constraints**, which autogenerate never renders. `alembic check` is
  built on the same diff, so it is blind to them too: a model whose `CheckConstraint` never
  reached the database reports clean.

## Which engine

The projects split by database, and the column-ordering rules differ completely. Check the
driver in the project's config before applying anything below:

- `mysql+aiomysql` / `pymysql` → **MySQL** section
- `postgresql+asyncpg` / `psycopg` → **PostgreSQL** section

## Keep the database column order identical to the model's

The base columns come first, then the model's own columns in declaration order. The model base
declares this — look for `sort_order` on the shared primary key (e.g. `sort_order=-100` forces
`id` ahead of every other column) and for the project's column-order test, where one exists.

`--autogenerate` never renders a column position and `alembic check` does not report order
drift, so this is on the migration author in both engines.

### MySQL

MySQL appends a new column at the end of the table and `op.add_column()` has no positioning
option, so a migration that adds a column must place it explicitly with raw SQL:

```python
op.execute("ALTER TABLE `client_jobs` ADD COLUMN `code` varchar(20) NULL AFTER `deleted`")
```

The position is the one the model declares: after the column preceding it in the class, or after
the last base column when it is the model's first own column.

Raw SQL is the only route — no `op.*` method can position a column:

- `op.add_column()` and `op.alter_column()` have no positioning parameter, and Alembic's MySQL
  `MODIFY` / `CHANGE` renderer emits only type, nullability, default, autoincrement and comment.
  A `mysql_after=` kwarg on `op.alter_column()` raises no error and produces **no SQL at all** —
  it is silently dropped.
- `sa.Column(..., mysql_after=...)` is rejected: the MySQL dialect registers no `Column`
  arguments.
- `op.batch_alter_table(recreate="always", partial_reordering=[...])` does reorder, but by
  `CREATE _alembic_tmp_*` + `INSERT … SELECT` + `DROP TABLE` + `RENAME`. On these schemas it
  fails outright — MySQL check-constraint names are schema-global, so the temp table collides
  with the original's `ck_<table>_deleted` (error 3822), which every model inheriting the base
  has. Dropping and recreating a live table with inbound foreign keys, indexes and its
  AUTO_INCREMENT counter is also the wrong trade for a cosmetic ordering change.

Verify afterwards:

```sql
SELECT ORDINAL_POSITION, COLUMN_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = '<database>' AND TABLE_NAME = '<table>' ORDER BY ORDINAL_POSITION;
```

### PostgreSQL

PostgreSQL has **no `AFTER` clause and no way to reposition a column**. `ALTER TABLE … ADD
COLUMN` always appends, and the only route to a different order is recreating the table. So,
unlike MySQL, ordering is not something a migration can repair:

- **At table creation**, the order comes from the model — `sort_order` on the base PK puts `id`
  first, then the model's own columns in declaration order. Autogenerated `op.create_table()`
  preserves it.
- **For a column added later**, accept that it lands at the end. Do not recreate a live table to
  move it; the physical order carries no meaning in PostgreSQL, and `SELECT *` ordering is the
  only thing affected.
- If order genuinely matters for a consumer, have that consumer name its columns explicitly
  rather than migrating the table.

Verify with:

```sql
SELECT ordinal_position, column_name FROM information_schema.columns
WHERE table_name = '<table>' ORDER BY ordinal_position;
```

**Constraint names.** The base's `MetaData(naming_convention=…)` makes Alembic emit deterministic
index and constraint names, which is what keeps migrations reversible — a downgrade can only drop
a constraint whose name it can predict. Never hand-name a constraint in a way that bypasses the
convention.

**`compare_type=True`** is set in `migrations/env.py`, so type changes are detected. Server
defaults are **not** compared unless `compare_server_default=True` is also set — check before
assuming a `server_default` change will be picked up.
