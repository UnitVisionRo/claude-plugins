# FastAPI + Nuxt Scaffold

## Overview

Scaffolds a two-tier app: an async FastAPI backend exposing **two separate API surfaces**
as sub-apps (each with its own CORS posture, auth dependency, and OpenAPI schema), and a
Nuxt 4 + Vuetify 4 frontend whose entire API client (TS types, validation schemas, typed
SDK) is **generated** from one of those surfaces' OpenAPI schema — never hand-written.

Core principle: the OpenAPI schema is the contract. Nothing about the wire format is
duplicated by hand between backend and frontend.

It ships a **working authentication flow**, not a placeholder: invite-only signup, Argon2
passwords, httpOnly cookie sessions with rotating refresh tokens, and two-factor auth by
authenticator app (TOTP) or emailed code — plus the screens for all of it. A seeded `admin`
account with a random password gets you in on the first run.

## When to use

- Starting a brand-new app that wants: a browser-facing admin/console API, a separate
  server-to-server integrations API, and a Nuxt+Vuetify frontend consuming the former.
- Replicating this exact architecture pattern into a fresh project — not extending an
  existing app that already has it.

Not for: adding a single new endpoint or page to an existing app (just follow the existing
app's own conventions), or apps that only need one API surface with no external
integrations.

## Required inputs — ask before creating anything

This skill needs exactly two things: **`appName`** (kebab-case, used as the directory name,
project name, and title strings) and **`targetDir`** (absolute path to create the project in).

**If either is missing from the request, stop and ask the user before writing any file or
running any command.** Never invent a project name, never guess a directory, never scaffold
into the current directory "as a reasonable default" — an unconfirmed `targetDir` is exactly
the kind of mistake that's expensive to undo (wrong location, wrong repo).

You also need a reachable PostgreSQL and credentials for it. Ask if they aren't obvious.

## Package versions: always via the package manager, never hand-pinned

`uv add` / `uv add --dev` and `npm install` / `npm install -D` are the ONLY way dependencies
enter `pyproject.toml` / `package.json`. Do not hand-write a version number into either file.
Hand-pinned versions go stale the moment they're written and drift from whatever's actually
installed — this is not hypothetical: an earlier version of this skill shipped a fully
pre-written `pyproject.toml`, and by the time it was tested months later its own hand-picked
mypy/pydantic-settings versions no longer agreed with each other, failing the skill's own
required `mypy` gate. Reference files below only ever hold **tool config** (ruff/mypy/pytest
sections, npm scripts) — never a dependency list.

Two surfaces, mounted as **separate FastAPI sub-apps** in `main.py` (see
`references/main.py` for the full pattern):

| Surface | Consumer | CORS | Auth |
|---|---|---|---|
| `/rest` | Browser (the `gui/` app) | locked to the frontend origin(s), credentials allowed | httpOnly session cookie (JWT bound to its session) + refresh-token rotation, optional 2FA; `routers/rest/deps.py` |
| `/api` | Server-to-server integrations | open (`*`, no credentials) | static API-key header check (`references/routers_api_deps.py`) |

The frontend (`gui/openapi-ts.config.ts`) generates its client **only from `/rest`** — an
integrating system generates its own client from `/api`'s schema separately. Never let the
GUI call `/api` or vice versa; if a route is genuinely needed on both, implement it once per
surface and share the underlying logic through a `services/` function.

## The authentication flow

There is **no public sign-up**. An administrator invites an email address; that creates a
real `users` row holding only an HMAC fingerprint of a single-use invite token. The invitee
opens the emailed link, picks a username and password, and the token is consumed — which is
the moment the row becomes an account that can log in.

```
POST /rest/users/invite ──► users row (inviteTokenHash set, no password)
                             │  email + the link is also RETURNED to the admin
GET  /rest/auth/invite/{t} ──► who the invite is for (public, for the signup form)
POST /rest/auth/signup     ──► username + password set, inviteTokenHash cleared
POST /rest/auth/login      ──► session cookies,  OR  {twofaRequired:true} + a waiting ticket
POST /rest/auth/2fa/verify ──► session cookies
```

Forgotten passwords take the same shape — a single-use, fingerprinted, expiring token in an
email — and every signed-in browser is listed and revocable:

```
POST   /rest/auth/recovery        ──► always 200, mails a link only if the account is real
GET    /rest/auth/recovery/{t}    ──► is this link still good? (so the page can say so first)
POST   /rest/auth/password-reset  ──► new password, token burnt, ALL sessions revoked
GET    /rest/auth/sessions        ──► one row per signed-in browser, current one flagged
DELETE /rest/auth/sessions/{did}  ──► sign that browser out now ("all" = everywhere else)
```

Decisions worth knowing before you change anything:

- **Sessions are httpOnly cookies, not bearer tokens in JS.** A token JavaScript can read is
  a token an XSS can exfiltrate. The cost is that CSRF becomes the browser's problem, handled
  by `SameSite` (`COOKIE_SAMESITE`).
- **Login with 2FA issues no session at all** until the code is confirmed — only a
  short-lived JWT with its own audience, which `get_current_user` rejects by construction.
- **Nothing reversible is stored that doesn't have to be.** Passwords: Argon2. Refresh and
  invite tokens: keyed HMAC fingerprints. TOTP secrets: Fernet-encrypted, because verifying a
  code requires reading the secret back.
- **A used TOTP time step can never be reused** (`lastTotpTimestep`), so a shoulder-surfed
  code is dead on arrival.
- **Email delivery is best-effort** and never fails a request; the invite endpoint returns
  the link so the flow works before SMTP exists.
- **Renewing an expired access token happens only in the browser.** `POST /auth/refresh`
  rotates the refresh token and returns the replacement in a `Set-Cookie`; during SSR that
  header would land on the Nuxt server's own response and never reach the browser, revoking
  the visitor's token without replacing it. So SSR reaches *no verdict* in that case and
  `plugins/auth.client.ts` settles it after hydration — which is also why the public/protected
  rule lives in `utils/routeAccess.ts`, shared by the middleware and that plugin.
- **Validation is declared once, in `api/schemas/rest.py`, and generated into the frontend.**
  `Annotated[str, StringConstraints(pattern=...)]` becomes `v.regex(...)` in the generated
  valibot schema, so the browser enforces the server's own rule without restating it. A
  `field_validator` produces no JSON Schema and so becomes `v.string()` -- invisible to the
  client. Two consequences worth remembering: `schemas/rest.py` sets
  `regex_engine="python-re"` (Pydantic's default Rust engine rejects the look-ahead the
  password rule needs), and input normalisation must use `mode="before"` so it runs ahead of
  the constraint.
- **One role per user** (`Role.ADMIN` / `Role.USER`). A real permission model is domain
  modelling for the app being built, not for the scaffold.
- **The access token names the session that issued it** (a `did` claim), and
  `get_current_user` joins on it. Without that, revoking a session would only stop it
  *refreshing*: the access token already in that browser would keep working until it expired,
  so "sign this other device out" would silently mean "within half an hour".
- **`POST /auth/recovery` answers identically for a real and an imaginary account.** A 404 on
  an unknown username is an account-enumeration oracle that needs no credentials to query.
- **A password reset ends every session.** People reset passwords precisely when they think
  someone else has the old one.

## Steps

1. **Confirm inputs.** Get `appName` and `targetDir` (ask if not given — see above).

2. **Backend init.** `mkdir -p <targetDir>/api && cd <targetDir>/api`, then:
   ```bash
   uv init --app --name <appName> --vcs none --no-readme .
   uv add fastapi "uvicorn[standard]" "sqlalchemy[asyncio]" asyncpg alembic pydantic \
       pydantic-settings "pydantic[email]"
   uv add argon2-cffi pyjwt cryptography pyotp fastapi-mail jinja2
   uv add --dev ruff mypy pytest pytest-asyncio httpx
   ```
   This creates `pyproject.toml` (with real, current dependency versions) and a stub
   `main.py`/`.python-version`. Append the **entire contents** of
   `references/pyproject-tool-config.toml` to the generated `pyproject.toml` (tool config
   only — never touch the `[project]`/dependency sections `uv` just wrote).

3. **Copy backend reference files** over the `uv init` stub, replacing `__APP_NAME__` with
   the real `appName` wherever it appears (grep afterward to confirm none survive). **The
   architecture tree above is the complete reference-file → destination mapping** — use it.
   Most files also repeat their destination in a first-line `Destination:` comment; strip that
   line from the copies, it's an instruction to you, not part of the app.

   Then create the empty package files the tree above shows: `lib/__init__.py`,
   `schemas/__init__.py`, `schemas/api.py`, `services/__init__.py`, `routers/__init__.py`,
   `scripts/__init__.py`, `tests/__init__.py`, and:
   ```python
   # routers/api/__init__.py
   from fastapi import APIRouter, Depends

   from routers.api.deps import verify_api_key

   router = APIRouter(dependencies=[Depends(verify_api_key)])
   ```
   Plus `.gitignore` at `<targetDir>/` (from `references/gitignore.root`) and
   `<targetDir>/api/` (from `references/gitignore.api`).

4. **Backend env.** `cp .env.example .env`, then fill in:
   - `DB_USER` / `DB_PASSWORD` / `DB_NAME` — no defaults; the app fails to import without them.
   - `TOKEN_KEY` — generate one: `python -c "import secrets; print(secrets.token_urlsafe(64))"`.
     There is deliberately no default. It signs JWTs, keys the token fingerprints, and derives
     the TOTP encryption key; rotating it invalidates every session, pending invite and
     enrolled authenticator.
   - Mail settings, if you have an SMTP host. If you don't, leave them — sending is
     best-effort and the invite endpoint returns the link anyway.

   Create both databases (`DB_NAME` and `TEST_DB_NAME`) before the next step.

5. **Migrations.**
   ```bash
   uv run alembic init -t async migrations
   ```
   Overwrite the generated `migrations/env.py` with `references/migrations_env.py` (points
   Alembic at the app's own `lib.database.engine` and `models.base.Base.metadata` instead of
   a URL hardcoded in `alembic.ini`). Then:
   ```bash
   uv run alembic revision --autogenerate -m "initial schema"
   uv run alembic revision -m "seed enum values"
   ```
   Paste `references/migration_seed_enum_values.py`'s body into that second file, keeping the
   `revision` / `down_revision` values Alembic generated. **Replace `down_revision` before
   `revision`** — `"revision = \"<generated>\""` is a substring of the `down_revision` line, so
   doing it the other way round silently produces a self-referencing migration that fails with
   "Self-loop is detected in revisions". Then `uv run alembic upgrade head`.

6. **Seed the administrator.**
   ```bash
   uv run python -m scripts.seed --email <a real-domain address>
   ```
   Prints a random password **once**. Save it — it is not stored anywhere in plaintext.
   (`--reset-password` issues a new one later.)

7. **Frontend init.** `mkdir -p <targetDir>/gui && cd <targetDir>/gui` — the directory MUST
   be empty at this point (nothing copied into it yet), then:
   ```bash
   npx nuxi@latest init . --template minimal --packageManager npm --gitInit=false --no-install --force
   ```
   (`--force` is safe here only because the directory is still empty — never run this after
   copying any of this skill's own files into `gui/`, or `nuxi` will overwrite them.)

8. **Install frontend dependencies** (still inside `gui/`):
   ```bash
   npm install @mdi/font pinia sass-embedded valibot vite-plugin-vuetify vuetify vue qrcode.vue
   npm install -D @hey-api/openapi-ts @nuxt/eslint @pinia/nuxt @unocss/nuxt \
       @unocss/preset-attributify @unocss/preset-icons @unocss/preset-wind4 unocss \
       vitest vue-tsc typescript eslint
   ```
   (`nuxt`/`vue` are already present from `nuxi init`; re-installing `vue` here is harmless.
   Some devDependencies above may already be present from the `nuxi` template — `npm install`
   no-ops on those, it doesn't duplicate or downgrade.)

9. **Layer the frontend reference files on top**, replacing the nuxi-generated file of the
   same name — again per the architecture tree, stripping the `Destination:` first line. Also:
   - Copy `references/CLAUDE.gui.md` to `gui/CLAUDE.md`.
   - Merge `references/package-scripts.json`'s `"scripts"` entries into the generated
     `package.json` (don't replace the whole file — `dev`/`build`/`generate`/`preview`/
     `postinstall` from `nuxi` stay as-is). Rename `package.json`'s `"name"` field from
     whatever `nuxi` set (the directory basename, `"gui"`) to the real `appName`.
   - `gui/eslint.config.mjs` does not exist yet at this point — `@nuxt/eslint` only
     generates it once Nuxt runs with the module registered (which the `nuxt.config.ts` you
     just copied does). Run `npx nuxt prepare` once to generate it, THEN edit it per
     `references/eslint-generated-ignore.md`.
   - Append `references/gitignore.gui-additions`'s contents to the `nuxi`-generated
     `gui/.gitignore` (see the comment in that reference file — git needs each intermediate
     directory re-included, not just the snapshot file).

10. **Generate the API client.** Start the backend (`cd api && uv run uvicorn main:app`), then
    from `gui/`: `npm run openapi`. This snapshots `/rest/openapi.json` and generates the
    typed SDK the frontend files already import. It must run before `npm run dev` or
    `typecheck` — until it does, every `~/generated/rest` import is unresolved.

11. **Fill in the root `CLAUDE.md`'s** one-line "what this is" placeholder once the app's
    actual purpose is known.

## Verification

Don't report the scaffold as done until all of these pass:

**Backend**
- `cd api && uv run uvicorn main:app` boots; `curl localhost:8000/health` returns
  `{"status": "ok"}` and `/health/db` returns `{"database": "ok"}`.
- `uv run pytest` passes — including `test_auth_flow.py`, which walks invite → signup →
  login → TOTP and the email-code path end to end.
- `uv run ruff check . && uv run mypy .` clean.
- `curl localhost:8000/rest/openapi.json` shows clean operation ids (`login`, `invite_user`),
  not `login_auth_login_post`.

**Frontend**
- `cd gui && npm run dev` boots; `curl localhost:3000/login` returns 200 with Vuetify's SSR
  classes present (`v-application`, `v-theme--*`) — proves Vuetify is actually wired in, not
  just that the config parses. Use `/login`, not `/`: an anonymous request to `/` is a
  redirect.
- `npm run typecheck` and `npm run lint` clean.
- `npm run openapi` succeeds against the running backend and regenerates the client.

**The flow itself** — this is the part that actually proves the scaffold works, and it cannot
be checked by curl alone. In a browser:
1. Visiting `/` while signed out lands on `/login`.
2. The seeded `admin` account signs in and the dashboard shows role `ADMIN`.
3. `/users` → invite an address. The invite link is shown on screen.
4. Opening that link **in a signed-out session** shows the signup form, prefilled with the
   invitee's email.
5. Submitting it creates the account; that user can then sign in.
6. `/account` → turn on two-step verification, scan/enter the TOTP key, confirm the code.
7. Sign out and back in: the password alone now stops at a code prompt with **no session
   cookie set**; a wrong code is refused; the right code completes the sign-in.
8. That non-admin user is bounced off `/users`.
9. `/login` → "Forgot your password?" → the confirmation is worded the same for a real account
   and a made-up one. Following a real link sets a new password; the same link then fails.
10. `/account` → "Where you are signed in" lists this browser and any others. Signing another
    one out makes it land back on `/login` on its **next request**, not half an hour later.

## Optional: in-app help documentation

The `help-docs` plugin (`/install-help-docs`) adds user-facing documentation to the scaffolded
app: Markdown in `docs/help/`, compiled at build time, with a Help button in the app bar giving
contextual help per page and a searchable `/help` browser. It is a separate plugin because it
is not specific to this scaffold — but it installs cleanly onto it, and the layout and lint
configuration this skill produces are exactly what its steps expect.

## Common mistakes

**Scaffolding**
- **Scaffolding into an unconfirmed directory.** Always resolve `targetDir` with the user first.
- **Hand-writing a dependency version** into `pyproject.toml` or `package.json` instead of
  `uv add`/`npm install`. See "Package versions" above.
- **Leaving `__APP_NAME__` placeholders un-replaced** — grep for the literal string after
  copying, don't eyeball it. Likewise strip each reference file's `Destination:` header line.
- **Running `nuxi init --force` after `gui/` already has this skill's files in it** — it will
  clobber them. Always init first, into an empty directory, then layer files on top.
- **Editing the `revision` placeholder before `down_revision`** in the enum-seed migration —
  see step 5. The failure is "Self-loop is detected in revisions".
- **Running `npm run openapi` before the backend is up**, or `npm run dev`/`typecheck` before
  `npm run openapi` has ever run.

**Traps that fail silently** — each of these was hit while building this scaffold:
- **Overriding `get_session` on the root app in tests.** A mounted sub-app is a separate
  FastAPI instance with its own `dependency_overrides`; the parent's do not reach it. Override
  on `app.state.rest_app`, or the tests quietly run against the real development database and
  fail with nonsense like "incorrect username or password". `tests/conftest.py` does both.
- **Writing a rule in a `field_validator` when a constraint would do.** It works, the tests
  pass, and the frontend silently gets `v.string()` -- so the rule has to be typed out again in
  the browser, where it can drift. Reach for `field_validator` only to normalise input
  (`mode="before"`) or to compare fields (`model_validator`).
- **Restating rules in a submit handler** (`if (!form.email || form.password.length < 8) return`).
  That is a third copy, after the field rules and the server. One `validatePayload` against the
  generated schema replaces it.
- **Treating a valid JWT signature as a valid session.** Revocation (session revoke, logout,
  password reset) has to be visible to `get_current_user`, or it only takes effect whenever
  the access token happens to expire. The token carries a `did` claim and the dependency joins
  against a live `user_sessions` row; `test_recovery_and_sessions.py` pins this.
- **Making the recovery endpoint informative.** "No such user" is the single most useful
  reply you can give an attacker enumerating accounts, and it is reachable anonymously.
- **Calling `POST /auth/refresh` during SSR.** It rotates the refresh token, and the
  replacement arrives in a `Set-Cookie` the browser never sees — so the visitor is left
  holding a token the backend already revoked, i.e. logged out *harder* than if nothing had
  been tried. Equally: forgetting to call it at all on the client, which is easy to miss
  because everything works until the access token expires (30 minutes by default) and the
  refresh token then sits unused for its whole 30-day life.
- **Putting the visitor's `Cookie` header on the generated API client for SSR.** That client
  is a module-level singleton shared by every request the Nuxt server handles, so one
  visitor's cookie leaks their session to whoever is rendered next. Pass request headers per
  call instead — `middleware/auth.global.ts` → `stores/auth.ts`.
- **Leaving UnoCSS's Wind4 reset enabled.** It is emitted *unlayered*, and an unlayered rule
  beats anything inside an `@layer` — so it silently overrides Vuetify's `@layer vuetify-*`
  styles. The app still looks nearly right; what breaks is `.v-main`'s
  `padding-top: var(--v-layout-top)`, so content slides under the app bar. `uno.config.ts`
  disables it and explains why.
- **Using `@hey-api/client-nuxt`.** Its generated SDK does not typecheck under
  `nuxt typecheck` (it passes `DefaultT` into `RequestResult`'s error slot), and the errors
  are inside generated code you cannot fix and cannot exclude — `exclude` does not stop tsc
  checking a file something imports. `client-fetch` with `throwOnError` + `responseStyle:
  'data'` is both clean and nicer to call.
- **An admin or test email at `.test`, `.localhost`, or a bare hostname.** `EmailStr` rejects
  reserved and dotless domains, so the row is created happily and then 500s the first time a
  response model serializes it. Use a real domain or `example.com`. `scripts/seed.py`
  validates up front for this reason.
- **Leaving pytest-asyncio's loop scope at its per-function default** while sharing a
  session-scoped engine — every query dies with "attached to a different loop". The pytest
  config in `pyproject-tool-config.toml` sets both scopes to `session`.
- **Reusing the TOTP code that confirmed enrolment** to then sign in. Replay protection
  refuses an already-spent time step; that is correct, and tests must ask for the next step
  (`counter_offset=1`), not repeat the same one.

**Design decisions that are deliberate — don't "fix" them**
- **The invite endpoint returning the invite URL.** It is what makes the flow usable before
  SMTP is configured and when delivery fails, both of which are normal.
- **`lib/mail.py` swallowing send failures.** A bounced invite email is not a reason to 500
  an invite that was otherwise created correctly. If you later need delivery guarantees, that
